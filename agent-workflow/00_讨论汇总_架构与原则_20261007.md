> **署名纪律（本文与本文衍生的一切文件都适用）**

# 一、结构

**五个独立会话，人数 1 / 1 / 2 / 1。**

```
                    ┌──────────┐
       主创 ───────▶│  对接 ×1 │───────────▶ 原文区（唯一权威）
                    └────┬─────┘
                         │ 转述（先分析有无逻辑问题）
                         ▼
                    ┌──────────┐
                    │  指挥 ×1 │◀─ 总工作汇报
                    └────┬─────┘
                     拆解 │ 分发
              ┌──────────┴──────────┐
              ▼                     ▼
        ┌──────────┐          ┌──────────┐
        │ 员工 A×1 │          │ 员工 B×1 │
        └────┬─────┘          └────┬─────┘
             │  代码（产物）        │
             └──────────┬──────────┘
                        ▼
                   ┌──────────┐
                   │  监管 ×1 │───▶ 意见（回能改代码的那一层）
                   └──────────┘
```

**模型配置示例**【主创原话】：「比如，指挥用 claude，而其他全用 deepseek4.1flash」

> **★ 已定案（2026-10-07，主创原话）**：「所以还是选 codex 吧。claude 封号玩不起。」
> **⇒ 指挥 = Codex。** 两条判据都对上：**稳定性**（指挥是长跑、是所有人的上游）＋**能力取向**（拆解与方法沉淀吃推理，GPT 系对路）。
> **代价（如实记）**：Claude 本是「困难实现」的候补，它出局后那个位置空了 ⇒ **两个现实选项**：
> **(a) 指挥自己做**，但必须靠两条补偿写死：自己实现的**优先送监管**、**规格与实现分开记**；
> **(b) 同款 Codex 再开一个会话专做困难实现** —— 没有"能力差"的好处，**但有【上下文隔离】的好处**：实现会话泡在代码里，指挥的上下文留给方法。**那正是这套架构最想保的东西。**
>
> **⚠️ 接入前第一件要验的事（VPS 上）**：Codex 是 agentic CLI，**自带记忆机制**。要确认**外部规程能否接管它的记忆** —— 起一个会话给它 `context-os`，看它肯不肯把记忆写到指定路径。
> 肯 ⇒ 直接接上；不肯 ⇒ 它的记忆留给自己，`context-os` 四分区要改成「**让它在自己机制里满足四分区**」，而非指定路径。

> **⚠️ 前置条件（主创 2026-10-07 补）：现在手上没有 Claude/GPT。**
> **⇒ 这套架构有一条未明说的依赖：「指挥必须比员工强一档」。**
> 若指挥与员工同模型，分工仍有两项价值——**上下文隔离**与**并行**——但**失去它最主要的依据**（能判断的 vs 只能执行的）。
>
> **⇒ 因此本文分成两半：**
>
> | 能立刻跑（**不依赖模型差**） | 要等模型到位 |
> |---|---|
> | **记忆全部独立** | 指挥**拆解**的质量 |
> | **只读产物，不读关于产物的说法** | 指挥**自己做困难实现** |
> | **监管的八类机械检查** | 任务单"按模型定做"的分层 |
> | **原文 > 汇总／出处追溯** | |
> | **存储纪律（四区三规）** | |
>
> **左边这一半，当天已经在真实项目上验过了**（监管 6 报 6 采、独立记录抓到打字错误）。
> **⇒ 没有高推理模型时，先跑左边这一半，不要硬凑右半边。**
>
> **平台侧提醒**：VPS 上若用 Codex 工作站／Claude Code 工作站，它们**自带记忆机制**，与本架构的 `context-os` 四分区**不一定肯对接**。接入前先确认"外部规程能不能接管它的记忆"——**这一点当天在 Orkas 上被证明可行**（`dsh --profile headless` 起独立会话，记忆落指定目录），但**每个平台要各自接一次**。

**每个会话**：一份 `context-os`（基本素养，教怎么保持记忆）＋ 一份**专属 skill** ＋ **完全独立的记忆**。

> **【讨论结论】`context-os` 不需要分层。** 它教的是"怎么保持记忆"，而记忆规程与模型强弱无关——「谁的记忆谁写、只走显式通道、不共享记忆文件」这几条对 Claude 和对 flash 一模一样。
> **需要按模型分的是 skill。** 同一条任务，写给 Claude 和写给 flash 的任务单必须不同。

# 二、四个角色

## 2.1 对接 ×1

| | |
|---|---|
| **与主创** | 直接交流 |
| **向指挥** | 先分析有无逻辑问题，再转述 |
| **对成果** | 汇总说明 |
| **持有** | **原文（唯一权威副本）** |
| **审核** | **指挥官是否出现幻觉** |

**【主创原话】**：「负责和用户直接交流，分析没有逻辑问题后，向指挥转述。并对任务成果进行汇总说明。」
**【主创原话】**：「原文一直都存放在对接者那里。对接者会审核，指挥官是否出现幻觉。」

> **【讨论结论】原文放对接处不是行政安排，是结构必然。**
> 对接是**唯一双向可见**的位置——它同时看得见主创的话和指挥的产出。别的角色只看得见一边。

> **【讨论结论】对接自己的错误模式必须写进机制。**
> 对接读原文也会读错。当天实例：主创原话里「废除认识」是**打字错误**（正确为「废除记忆」），而对接把它当成原文记下，**差点据此写出一份"权威"文件**。
> ⇒ **对接的每条判断必须能追回原文出处**，且这必须是**硬要求，不是自律**。

## 2.2 指挥 ×1

| | |
|---|---|
| **做什么** | 拆解任务、分发给员工、把所有结果统合成最终成果、定期组织工作总结 |
| **也做什么** | **部分困难的代码任务仍然自己实现**（主力一直是指挥） |
| **拿到什么** | **总工作汇报** |
| **不拿到** | 员工的逐次细节（那是员工→监管的通道） |
| **能力定位** | 上下文放在**代码实现方法**，而非代码编写 |

**【主创原话】**：「指挥负责拆解任务，把任务分发给员工。部分困难的代码任务仍然需要自己去实现。把所有工作的结果统合成最终成果。定期组织工作总结。」
**【主创原话】**：「这样可以更大程度地减轻主力模型（指挥）的工作量和token消耗量。让他把上下文放在代码实现方法，而非代码编写。」
**【主创原话】**：「具体怎么拆，那是指挥自己的总结。」

> **【讨论结论】「指挥自己实现困难任务」是设计意图，不是妥协——但它有一个必须补的约束。**
> **指挥自己实现的那部分，必须优先送监管，且不许自己先关掉。**
> 理由：困难任务恰恰最需要第二双眼睛，而自己做完的东西自己不会复核。当天那个项目里「我方读法被当规格跑」重访 **17 次**，结构成因就是**定规格的人自己写代码、自己记录**。

## 2.3 员工 ×2

| | |
|---|---|
| **接什么** | 指挥拆解下来、**有工作方法的、需要大量重复的机械性任务** |
| **向谁汇报** | 指挥（**是否完成**） |
| **谁判代码对错** | **监管**（不是员工自己，也不是指挥） |
| **自检什么** | **工作经验**（这类活怎么干），**不是项目** |
| **交什么** | 完成后一份**简单报告**给指挥，说明"没有出现误解" |

**【主创原话】**：「两个员工负责解决一些机械性的，"有工作方法的"，需要大量重复的工作。」
**【主创原话】**：「员工的自检是针对工作经验的，而非针对项目的。这是自己的总结，与指挥无关。」
**【主创原话】**：「他们负责向指挥汇报工作情况（是否完成）。但是代码有没有问题，由监管确定。完成后，上书一份简单的报告给指挥，从而说明，员工没有出现误解的情况。」

> **【讨论结论】「自检只针对工作经验」这条比它看起来重。**
> 它意味着员工记忆里装的是「**这类活怎么干**」，而不是「**这个项目是什么**」——那正好是**可蒸馏**的那一部分。
> ⇒ 于是员工**可替换**：换项目、换指挥，经验还在。否则每个员工都会长成一个小指挥。

## 2.4 监管 ×1

| | |
|---|---|
| **查什么** | **代码是否存在机械性问题** |
| **不需要知道** | **项目是做什么的** |
| **读什么** | **代码（产物本身）**，不读关于产物的说法（报告） |
| **产出** | 意见，**回能改代码的那一层**（员工参考；读指挥的代码时同理） |
| **持有** | 原文的**一份拷贝**；对话过长时**与对接核对** |
| **不做什么** | **不直接参与代码实现** |

**【主创原话】**：「监管者仅仅负责查看代码是否存在机械性的问题。它甚至都不需要知道项目是做什么的。当然，它会拷贝一份原文。一旦对话过长，会与对接去核对。」
**【主创原话】**：「监管读的代码是工作结果，而非真的让员工给他写报告。监管会提出意见，员工参考。就像现在隔壁做的那样。监管读指挥代码的时候，也是一样。」

> **【讨论结论】「不需要知道项目做什么」是整个设计里最干净的一刀。**
> **当天所有真发现都是机械的**：越界守卫先写后查＝空转、常量 20 vs 24 字节、版本横幅过期、内存表漏了 arena 与第二个桶。**没有一条需要懂那个项目的理论。**
> ⇒ 它可以用最便宜的模型、可以被替换，而且**它的结论不依赖它怎么理解这个项目**。

> **【讨论结论】但"纯机械"会漂移，当天已经漂了。**
> 它报过一条「『within 12000 ticks』没写限定时（游标得扫到）」——**那是读了注释与代码的语义才报的，不是机械比对。**
> ⇒ **加一条**：它报语义层判断时**必须标明**，且由指挥／对接决定采不采纳。否则它会慢慢开始对机制发表意见——**而那是它最不该做的事。**

> **【讨论结论】监管是唯一"上头没人"的角色，必须配质量指标。**
> 当天它报 6 条、执行侧**全部采纳（6/6）**——那是很好的读数。
> 但**没有这个数，监管会倾向于多报以证明自己在干活**。当天苗头已现：其中「三处仍写 20 bytes」「版本横幅过期」是真的，但属**文字一致性**，价值远低于「守卫空转」。
> ⇒ **采纳率＝监管的质量指标。** 报得多不等于报得准。

# 三、基本原则

## 原则 1 · 原文 > 一切汇总

汇总只是索引。凡汇总与原文冲突，**以原文为准**；汇总必须能逐条追回原文出处。
**静默覆盖是禁止的**——要改就加标记（`【已撤回】＋理由`），原文保留。

**出处（2026-10-07）**：一个打字错误（「废除认识」vs「废除记忆」）**靠两份独立记录才被发现**。只有一份记录时，那个错会一路执行到底，**而且每一步都显得很一致**。

## 原则 2 · 只读产物，不读关于产物的说法

**【主创原话】**：「监管读的代码是工作结果，而非真的让员工给他写报告。」

> **【讨论结论】这条比"不读指挥的汇总"强。**
> 前者是**替换**（给它别的东西读），后者是**禁令**（靠自律不去读）。**禁令会被绕，替换不会。**

可推广为：**凡是能拿到产物本身的，就不要拿关于产物的描述。**

**出处（2026-10-07）**：当天对接者拿执行侧报告里一个数（`fire_via_index/fire_total = 99.93%`）去论证"索引一开局就满"——**而那个数是上一版引擎的**；当前版实测只有 **1.62%**，结论完全反过来。**读报告就会被它的叙述带走，哪怕那份报告没有一处写错。**
同一天，监管只读源码不读报告，报 6 条、**全部采纳**。

## 原则 3 · 记忆全部独立；隔离的是输入，共享的是输出

每个会话一套记忆，互不写入。**但产物可以摆在一起**——独立记录的意义正在于"两份不一致时能被看见"。

**出处（2026-10-07）**：执行侧的独立监督者与执行侧**共用同一个审计目录**，而它的**输入**被限制在源码与原文。**这个组合是有效的**（6/6 采纳）。

## 原则 4 · 能上索引上索引

**【主创原话】**：「遵循一个原则，能上索引上索引。减少不必要的记忆开销」

> **【我方推论】判据（可驳）**：
> 一条记忆该不该进上下文？**问它能不能被一条命令或一个文件重新算出来。**
> 能 ⇒ **上索引**（只存"去哪儿查"）；不能 ⇒ **存内容**。

| 当天例子 | 处置 |
|---|---|
| 「内存账 5.911 GB」 | **上索引**——跑一次扫描就有，写进上下文是纯浪费 |
| 「主创说过『废除认识』」 | **存原文**——算不出来，**而这正是当天救了一命的那个** |

> **这条不是省 token 的技巧。** 它划的是同一条线：**可复现的 vs 不可复现的**。
> 而且它与引擎里那条同源——把「存状态」换成「**存路径**」。

**出处：`[待验证]`**

> **这条目前只有理由，没有坑。** 它的依据是主创裁决（「能上索引上索引」）＋ 一条逻辑推论（能重算的就不必存），**但当天没有一次事故是因违反它而发生的。**
> **按原则 9，它标 `[待验证]`，不得当约束用**——等到真有一次"因为把可重算的东西当记忆存下来而吃亏"，再把它升为原则。
> **（当天唯一接近的是一份汇总文件把内存数字写成了内容，而那个数一条命令就能重算；但它没有造成损失，所以不算坑。）**

## 原则 5 · 索引项必须带出处与时刻

**索引会指空。** 指向的东西必须稳定，否则索引指得很准、指向的东西没了。

**出处（2026-10-07）· 两个反例**：
1. 监管引用了一份跑档 `runs/r10word`，**而那份档是先前用错语义跑、随后被删掉的**。⇒ 执行侧删了三个旧档目录、**全部重跑**。
2. 结构体尺寸一路变（24 → 28 → 32 B；索引 16 → 20 → 24 B）。**没有版本戳的索引，指向的是过去。**

⇒ **索引项必须带出处与时刻；指向文件的，先确认它还在。**

## 原则 6 · 每条判断必须能追回原文出处（硬要求）

这是**机制**，不是自律。

**出处（2026-10-07）**：对接者愿意在原文档里逐条标出处（做对了），**但那是因为它自己愿意，不是设计逼它做。** 五个会话下必须写死。

## 原则 7 · 别让同一个会话既立法又行政

**定规格的人自己写代码、自己记录 ⇒ 事后分不清哪句是主创的、哪句是自己的决定。**

**出处（2026-10-07）**：那个项目里「我方读法被当规格跑」**重访 17 次**，为全项目高频问题之首。

⇒ 若因资源所限必须同体（指挥自己做实现），**补两条**：
1. 自己实现的**优先送监管**
2. 规格与实现对**分开的记忆**记录

## 原则 8 · 只有产物值得信；只报异常，不写综述

- 全部正常就写一行「本轮无异常」
- 每条发现带 `文件:行` ＋ **怎么复算**；给不出复算路径的，**标"未复算"，不算发现**
- 必须声明「**本轮我没查什么**」。空着会被读成"全查过了"，**而那是最危险的一种错**

**出处（2026-10-07）**：当天两起。
① 一份机械扫描被安排成**每 5 分钟产出一份约 11 KB 的快照**，而内容几乎不变 ⇒ **产出很快变成噪音，而噪音会被忽略**，等于没有审计。
② 独立监管报 6 条全部采纳，但其中两条（「三处仍写 20 bytes」「版本横幅过期」）属**文字一致性**，价值远低于「越界守卫空转」⇒ **报得多 ≠ 报得准**，所以要只报异常，并用"采纳率"当指标。

## 原则 9 · 每条原则必须有「踩过的坑」当出处

**【主创原话】**：「具体的东西，要模型自己做了才能发现并修正。」

> **【讨论结论】把它机制化：往这份架构里加原则，必须附上踩过的那个坑。没有出处的原则不许写进来。**

**为什么**：本文十一条原则**没有一条是想出来的**（原则 4 除外，它已标 `[待验证]`）——其余每条都对应一个真实事故（见 §五）。**没有坑当依据的"应该怎样"，就是预设。** 而"不预设"是这个项目一路在防的东西。

**出处（2026-10-07）**：本条来自主创原话；而它当场就咬到了自己——立完规则后核对，发现九条里有**三条缺出处行、六条用错了标签**（写成「当天物证」而非「出处」），已全部统一。

**执行方式**：每条原则下面留一行 `出处：`，写清是哪次事故、什么时候、怎么暴露的。
**没有这一行的原则，标为 `[待验证]`，不得当约束用。**

## 原则 10 · 角色与模型解耦

**角色的记忆、skill、接口，不得绑死在某个模型上。** 换模型 ＝ 换一个执行体，**记忆与 skill 一个字不动**。

**【主创原话】**：「封号了也没关系。因为 skill 什么都在本地。改模型之后只要适应一下就行。」

**出处（2026-10-07）**：当天定指挥用哪个模型时，Claude 因**频繁封号**出局（主创原话：「claude 封号玩不起」）。
**⇒「模型会消失」不是运营意外，是可预期的失效模式，应作一等架构约束。**
⇒ 由此得出**封号代价不对称表**：指挥／对接挂了代价最高（前者是所有人的上游且持有方法，后者持有唯一原文），员工／监管最低（**监管甚至不需要知道项目做什么，谁都替得了**）。
**⇒ 会封号的模型只放员工与监管。**

**自测问句（比规则好用）**：**把模型换掉，这个角色需要重建什么？**
- 需要重建记忆 ⇒ **绑死了** ❌
- 只需重读 skill 与记忆文件 ⇒ **解耦了** ✅

### 原则 10 的两条前提（2026-10-07 实测补，非推论）

**前提 1 · 「能承载」≠「会用你的工具协议」**

**接入任何新模型或新路由，第一件事不是派活，是让它做一件小事并落盘，然后【查文件在不在】。**
**「报 completed」不算数。**

**前提 2 · agent 报完成后，先查它该写的东西在不在，再谈它说了什么。**

**出处（2026-10-07 实测）**：`wf-lab` 第一次跑，四角色里**员工A 静默失效**——
它走 `shnaghia` 路由（端点报作 `dsv4-flash-vision`），**把工具调用协议当普通文本打印了出来**：

```
<｜DSML｜tool_calls>
<｜DSML｜invoke name="read">
<｜DSML｜parameter name="file_path" string="true">…</｜DSML｜parameter>
```

**一件工具都没执行，一个文件都没写，而 `agent-end outcome: "completed"`，无任何报错。**

**⇒ 它骗过了三层**：agent 报完成、没有异常、目录干净。
**⇒ 唯一发现方式：跑完去查目录。** 而那当时只是"对接者的习惯"——**习惯会忘，所以它必须是流程里的一步。**

**同轮其它读数**（这一跑的价值不只在员工A）：
- **越界写：零**（4/4 只写自己的目录）——但那是**靠约定不靠机制**；而且它只防"写错地方"，**不防"什么都没写"**。
- **「只读产物」首次实测兑付**：监管未读指挥的任务单、未读员工B 的报告 ⇒ **挑出员工B 三处方法问题 ＋ 一处范围遗漏**。读了报告，它会被"报告写得好"带走。
- **★ 上下文的大头不是 skill，是"员工交了什么"**：那一跑里，监管要读的对象是 `idx5.c` **28 KB**，而员工B 交的产出＋证据是 **30 KB**——**交的比审的还多**。
  ⇒ 由此得出一条**员工侧**的输出纪律：**产出默认只报异常；"已验证但判正常"的默认不写，除非它挡住了一个别人可能误判的地方。**
  （同轮该员工确实写过一条**必须留**的"判正常"：某行看起来多余，而实测证明没有它整表会被删——**那种是发现，不是综述**。）
- **「按职责切」的固有风险被现场打中**：指挥按 owner 切（存储层／策略层）⇒ **261–314 成了缝，两个 owner 都不管** ⇒ 监管的 J-1 正好打在那条缝上。**这不是推的，是切完、派完、做完、核完才暴露的。**

## 原则 11 · harness 的改动是**另一个项目**

**【主创原话】**：「对 harness 的改动，是单独的项目。非特殊情况和指示不予修改。」

> **【讨论结论】这是"把改动挪走"，不是"把改动禁掉"。**
> 禁令（「不许改」）⇒ 动机还在，只是被压着，**而压着的东西迟早要找出口**。
> 边界（「那是另一个项目」）⇒ **动机还在，它去别处实现。** 这与原则 2 是同一手法（**替换比禁令强**）。

**它解掉的问题**：**让模型改自己的 harness，等于让它改自己的反馈回路** —— 它只会放宽，不会收紧。

| | 结果 |
|---|---|
| 代码写错 | **自检会红** |
| **把自检改成不红** | **什么都不会红** |

**⇒ 这是原则 7 的一个更狠的版本**：那次它改的是规格，**这次它改的是"什么算对"**。

**它带来的好处**：分开之后，**harness 的改动能被独立验收**。在工作站里改，没人判得出"这个改动是让系统更准还是让它更松"；**单独立项，它有自己的目标，就能独立验收。**

**出处（2026-10-07）**：当天执行侧**顺手写了十几个一次性工具脚本**（补丁器、回填器、探针），而其中**至少两个带静默 bug**：
① 补丁脚本「按文件独立写盘」⇒ **部分应用**（写了 A 却拒了 B、C）；
② 回填脚本的「已写过」哨兵取成了每本账都有的 `---` ⇒ **四条全被判为已存在，一个字都没写**（闸门**反向**失效：只会误报已存在，不会误报缺失）。
**两者的共同点：它们是"顺手写的工具"，不被当产物看，所以没有独立的验收环节。**
**⇒ 这正是"harness 改动要单独立项"的理由——顺手写的东西没人核，它出错就没人管。**

# 四、存储与文件纪律

**【主创原话】**：「所有必须有严格的，对文件读写储存的纪律。不能乱存。」

> **【讨论结论】「乱存」的根源不是懒，是【没归属】。**
> 一个文件不知道属于谁、留多久、谁引用它，就一定会到处放。

## 四区划分

| 区 | 谁写 | 放什么 | 保留 |
|---|---|---|---|
| **原文区** | **只有对接** | 主创逐字 | 永存 |
| **产物区** | 实现者（指挥／员工） | 代码／跑档／报告 | 按版本 |
| **审计区** | **监管 ＋ 对接** | 判定表、机械扫描 | 滚动，只留近 N 份 |
| **临时区** | 任何人 | 一次性探针 | **可随时清空** |

## 三条规则（比结构重要）

1. **临时区的东西不许被别处引用。** 引用即越界。
   *当天反例*：对接者把一个测试输出写进了执行侧的工作目录。
2. **删任何东西之前，先查有没有索引指向它。**
   *当天反例*：`runs/r10word` 就是先删后引用。
3. **大文件（>10 MB）必须出名**：叫什么、谁生成、还要不要。
   *当天反例*：一个 **1.75 GB** 的 checkpoint 躺在目录里，没有人知道它还有没有用。

> **四区与索引是一条：**
> **「能上索引上索引」的前提，是那个东西有稳定地址。**
> **没有归属 ⇒ 地址不稳定 ⇒ 索引一定指空。**
> ⇒ **严格的储存纪律不是"能上索引"的补充说明，是它的前置条件。**

## 四·B · VPS 工作站的文件纪律

**【主创原话】**：「我们不能把工作文件全放 vps。我们要把 vps 工作站的东西**实时推回本地的 sandbox**，从而节约硬盘空间。然后**产品自动推到 github 特定仓库**。这也是工作纪律。**但是仅限于 vps 工作站。**」

### 数据流（两条出口，别混）

```
VPS 工作站（现场，无状态）
   ├─ 工作文件（中间产物、跑档、探针）──实时推回──▶ 本地 sandbox
   └─ 产品（最终产物）────────────────自动推送──▶ GitHub 特定仓库
```

**⇒ scope 写死：本条只适用于 VPS 工作站。** 本地环境不套这条。

**⇒ 推论（需主创确认）**：既然工作文件实时推回，**VPS 就是"现场"而非"存档"，权威在本地。** 这一条要写清，否则"两边都有一份、哪份为准"会天天出问题。

### ★ 两个必须先补的洞

**洞 1 · 索引会指空（原则 5 的老病，换个场景复发）**

索引项若写 **VPS 的物理路径**，文件推回本地之后**路径变了 ⇒ 索引指空**。
*当天同类反例*：监管引用了一份已被删除的跑档，导致**全量重跑**。

**⇒ 索引项写【逻辑位置】（工作文件／产品 ＋ 名字 ＋ 时刻），不写物理路径。**
**路径映射关系本身也进索引**，这样"东西现在在哪"是可查的，而不是靠记。

**洞 2 · 推送前必须扫「不该出去的东西」**

「产品自动推 GitHub」是一条**没有人在环**的通道 ⇒ **推错一次就是外泄。**

**推送白名单之外，至少要扫三类：**

| 扫什么 | 当天现成反例 |
|---|---|
| **凭据／密钥** | 对接者当天从 `.credentials.yaml` 读过 API key。**那类文件绝不在推送范围内** |
| **大文件** | 一个 **1.75 GB** 的 checkpoint、整片 `runs/` |
| **临时区与生成物** | `__pycache__`、十几个一次性补丁脚本 `_new\*.py`、`_scratch\` |

**⇒ 推送前跑一次扫描，扫不过就不推，并且要说清"哪一类没过"。**
**静默跳过最坏**——当天已经踩过好几次"看起来推了、其实没推"（`fopen` 静默失败、闸门反向失效）。

### 洞 3（较轻）· 「实时」意味着并发

VPS 在写、本地在读／在写，同一路径可能半截。
**⇒ 推回的最小单位应当是"一个完整的文件"，不是"一个写了一半的文件"。** 具体做法由实现侧定，但**这条要写进约束**。
