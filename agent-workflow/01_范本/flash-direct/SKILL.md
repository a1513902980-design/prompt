# flash-direct

**专门为 4.0flash 这类小模型定做的派单方式。**

核心不是"少给它活干"，是**把任务单里留给它的判断量消掉**。

## 一句话原理

> **推理需求量 = 任务单里留给它的判断量。**
> **判断量归零 → 推理归零。**

同一个任务（手写递归下降解析器，156~191 行），同一把 key，同一端点，只改任务单怎么写、开不开推理：

| 组 | 配置 | 耗时 | completion | **推理 token** | 质量 |
| --- | --- | --- | --- | --- | --- |
| A | 默认（不干预） | 402.8s | 14198 | 12762 | 18/18 |
| B | `--no-reasoning` | 163.7s | 4587 | 3101 | 18/18 |
| C | B + 输出纪律 | 45.9s | 2269 | 1165 | **15/18** ❌ |
| D | C + **完整**接口契约（带 docstring、树状图） | 181.2s | 6444 | **5030** | 18/18 |
| **E** | **输出纪律 + 紧凑名字清单** | **12.3s** | **1230** | **0** | **18/18** ✅ |

**A → E：33 倍快、11.5 倍省 token、质量一样是满分。**

## ⚠️ 最容易搞反的一条：说明越多 ≠ 越清楚

对比 D 和 E —— **两者想说的是同一件事**（钉死方法名），但：

| | 写法 | 它要花多少推理去消化 |
| --- | --- | --- |
| D | 带 docstring、方法体、树状图、警示段落的**文档** | **5030** |
| E | 一行一个名字的**清单** | **0** |

> **冗余的解释本身就是认知负担。对小模型，"写得详细"和"写得清楚"是两件事。**

**所以定做的第一原则：把契约写成清单，不要写成文档。**

## 推荐配方（E 组，直接照用）

```bash
node <flash-executor 目录>/scripts/dispatch.mjs \
  --task <任务单> --root <工作根> \
  --no-reasoning \
  --max-tokens 16000 --idle-ms 90000
```

任务单里必须有三样，按顺序放最前面：

1. **输出纪律**（禁止解释、直接产出）
2. **名字清单**（凡是"调用处/定义处要对上"的，全部提前钉死）
3. 编号的硬要求 + 可验收标准

### 什么时候可以省掉后两样

| 情况 | 用什么 |
| --- | --- |
| 交付物**没有内部接口**（一段文案、一张表、一次抽取） | 输出纪律就够 |
| 交付物**有多个函数/类/文件**，谁调谁 | **必须给名字清单**（不加就是 C 组的 15/18） |
| 说不清怎么机械验收 | 别用本 skill，用 `flash-executor` |

> 判据一句话：**你能写出一段代码判断交付物对不对吗？** 能，就用本 skill。

## 失败模式清单（实测，按出现频率）

| 症状 | 根因 | 预防写法 |
| --- | --- | --- |
| **`AttributeError: ... has no attribute ...`** | 调用了个自己没定义的方法名 | **名字清单**——这是唯一实测会静默丢掉的一层 |
| 抛错异常类型（该 `ValueError` 抛了别的） | 边界没写死 | 逐条列出「什么输入 → 抛什么异常」 |
| 交付物里有 `...` / 「同上」/「略」 | 没禁止 | 交付格式里写明「不许省略号、不许分片」 |
| 推理失控、正文被吃光返回空 | 任务单里有模糊处 | 消掉判断点；`--max-tokens` 给足 |
| 自己加了没要的功能 | 边界没写 | 边界里写「不要加我没要的」 |

## 定做版任务单模板

```markdown
# 任务单：<一句话说清输入 → 输出>

## 输出纪律（最高优先级，先读这段）

**禁止输出任何思考过程、分析、计划、铺垫或解释。**

- 不写「首先」「让我」「我需要」这类开头，**收到任务直接产出**
- 不解释为什么这么写，代码本身就是答案
- 只有 <result> 和 <memory_update> 两个块，前后不要有别的内容
- 察觉到自己在准备推理——跳过它

---

## 名字清单（逐字使用；调用处与定义处必须一致）    ← 有内部接口才要

```
evaluate(text: str) -> float
class _Lexer:  __init__(text)  tokenize() -> list[tuple[str, object]]
class _Parser: __init__(tokens)  parse() -> float
               _expression()   _term()   _factor()

连线: evaluate → _Lexer.tokenize → _Parser.parse → _expression/_term/_factor
```

⚠️ 写完逐个核对上面这几个名字。写错的后果是 `AttributeError` 而不是提示。

---

## 功能要求

1. …（每条都是可机械校验的断言）
2. 边界情形逐条列：<什么输入> → <什么结果/抛什么异常>
3. **禁止**：eval / ast.literal_eval / exec / 任何第三方库
4. 末尾带自测，至少打印 N 个用例结果

## 交付格式

```
<result>
完整文件全文。不许省略号、不许“其余同上”、不许分片。
</result>
<memory_update>
1-5 行结论
</memory_update>
```

## 边界

单文件，仅标准库。不要图形界面、不要 CLI 参数解析、不要 <没要的库>。

## 可验收标准

```
<能跑的命令> → <期望输出>
<异常输入>   → <期望异常类型>
```
```

> **注意：名字清单要短。** 一行一个，不写 docstring、不写方法体、不画大图。
> 长度本身有成本（见上面 D vs E）。

## 验收（必做）

驱动报 `status:"OK"` 只代表回复里有 `<result>` 块，**不代表能用**。

```bash
python <flash-executor 同级>/../c02_details/extract.py <落盘的.md> <输出文件>
python <你的验收脚本> <输出文件>
```

**验收脚本按重要性检查**：

1. **能不能跑起来**（语法、导入）——静默失败最常死在这
2. 每个用例输出对不对
3. **异常路径对不对**（该抛的抛没抛、类型对不对）
4. 有没有省略号占位
5. 有没有用了禁止的东西

> 第 3 条最容易被忽略：C 组的 `'(1'` 就是抛错了异常类型，看起来"处理了"实际没处理对。

## 这个模型的能力画像（实测）

| 维度 | 表现 |
| --- | --- |
| 单点逻辑（词法、算符优先级、一元负号嵌套） | ✅ 强 |
| 陷阱处理（`--3`、`2*-3`、`1..2`） | ✅ 强 |
| 规格遵循（字段、格式、禁用清单） | ✅ 强 |
| 自述质量（`memory_update`） | ✅ 高，准确且有洞察 |
| **跨部分一致性**（调用处/定义处对得上） | ❌ **弱 —— 唯一实测短板** |
| 默认推理倾向 | ⚠️ 极猛（能烧到 90% 预算） |
| 速度 | 慢（≈35 tok/s，推理关掉后才正常） |

> 一句话：**它是个很听话的熟练工，但不会自己检查自己的活。**
> 所以定做原则是——**把它当「手」用，不当「脑」用。**
